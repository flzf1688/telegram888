# 通讯录库房与 OpenAI 自动接待开发方向

2026-11-16，需求确认后的方向更新。当前仅 UI 原型已更新，真实服务尚未开发接入。

## 业务流程
通讯录导入、格式检查、分组、重复检测 → 确认可联系范围 → 固定账号跟进 → 收到回复 → OpenAI 自动理解需求并查询产品知识 → 自动答复 → 在客户有意向、需要报价或问题超出知识范围时引导到已配置客服主账号 → 记录客服实际接待。
首次联系由任务规则控制；Agent 负责授权会话内的自动接待，不自行扩大发送对象。

## 配置页面
- 通讯录库房：分组、标签、国家、号码、联系人、来源、联系许可、拒绝联系标记、负责账号、跟进阶段。拒绝联系按工作空间统一生效。
- OpenAI：服务端密钥引用、模型、连接测试、每日预算、每会话预算、超时与故障状态。当前 HTTP 演示页不收集密钥；真实配置入口需认证与 HTTPS。
- 产品知识：自有产品资料、批准的价格信息、常见问题、禁用承诺、语言及风格。
- 客服目标：默认主账号、分组覆盖、经验证的 Telegram 用户名/用户标识，停用与替代流程。目标由管理员配置，模型和客户消息无权修改。
- 自动接待：触发条件、最大连续回复轮数、人工接管、拒绝停止、重复引导抑制。

## 实现设计
采用 OpenAI Responses API 与受约束函数调用。模型提出回答或动作，服务端验证会话、权限、状态、预算后执行。
允许的能力：查询当前工作空间产品知识、提交待发送回复、请求引导至配置的客服、标记需人工处理。不给模型凭据、任意 SQL、任意网址请求或切换账号能力。
每个会话串行处理；入站消息按 Telegram 标识去重。生成任务绑定会话版本，人工接管或新消息到达后作废过期回复。发送通过持久化发件队列，记录平台消息 ID；未知发送结果先核对，不盲目重发。
默认最小化传入客户数据，只提供获授权会话的必要上下文；客户数据不作为产品知识或训练资料。配置保留期限和删除流程。
API 超时、限流或预算耗尽采用有限退避并进入可见待处理状态；不把请求失败写成回复成功。

## 转交状态与证据
待引导 → 已生成引导 → 平台确认已发联系方式 → 等待客户到达 → 已到达 → 客服已接待。
普通客服用户名链接不能证明客户到达。客服主账号接入系统且取得授权后，可使用收到的私聊和稳定用户标识核对；无可验证事件时保留等待状态，由客服人工确认。不能把 URL 点击或模型判断当作已接待。
客户提出报价/知识外问题时，可自动说明需要主客服确认并提供正确联系方式，而不要求每条消息人工审批。投诉、拒绝、接管和故障按规则停止自动推进。

## 开发与验收顺序
1. 完成通讯录命名和 Agent 配置原型（本轮）。
2. 账号真实接收与发件队列、通讯录分组及客户固定归属。
3. 服务端 OpenAI 配置、知识检索与模拟对话评测。
4. 白名单测试账号的自动答复与主客服引导。
5. 主客服到达确认、实际接待统计、预算监控后再逐步扩大运行。
验收覆盖：产品问题、报价引导、无知识回答、多语言、拒绝联系、重复入站、人工接管中模型返回、API 超时、发送失败、客服目标无效、伪造客服链接和跨工作空间访问。

实施所需配置：OpenAI 项目密钥（安全配置入口填写）、客服主账号用户名、自有产品资料。首版不锁定具体模型，按实际账号可用模型与评测确定。
